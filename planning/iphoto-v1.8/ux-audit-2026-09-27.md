## 问题头与处理

| 优先级 | 用户可见问题 / 复现 | 架构根因 | 本轮处理 |
|---|---|---|---|
| P1 | 分析画面后，点选或重新绘制预览可能等整批元素轮廓预计算结束；最多 16 个对象时等待不可预测。 | `precache` 将全部对象放在一条串行 worker 请求中；队列优先级只能在请求之间生效。 | 拆成每对象一条低优先级请求；每处理完一个对象，优先处理用户操作与最新预览。 |
| P1 | 大照片切到 S 点选时，后台预热仍会读取并转换整张原图，增加内存峰值与首个后台任务的耗时。 | worker 的 `warm` 输入是 `source.image`，实际分割输入是 1600px `proxy`；服务虽会缩图，但先执行全图 RGB 转换。 | 预热直接传 `proxy`，与点选使用同一图像对象和像素。 |
| P2 | 用户在预计算期间改动选区，已完成的元素轮廓会因为编辑代数变化而丢弃；重新分析又可能重复排队。 | 后台轮廓与编辑渲染共用 `_generation`，缺少画面元素版本；低优先级队列也不去重。 | 为元素清单加 `revision`；同源图、同清单的后台结果即使编辑代数变化仍可落缓存；清单/照片变化即丢弃旧队列；已缓存和已排队对象不重复计算。 |
| P2 | 元素预计算异常可能连续显示多次错误提示，并干扰正在进行的 AI 请求。 | 每对象失败被当作交互分割失败，后续后台队列仍继续。 | 后台失败只给一次非阻断提示并停止同批剩余任务，不清除用户的 AI 请求。 |
| P2 | 后台元素预计算时，选区模块会显示“取消当前计算”，但按钮只能取消一个对象，下一对象又继续，像是取消无效。 | `taskKind` 只看 worker 操作类型，没有区分后台与用户发起的分割。 | 低优先级任务不占用选区的前台任务栏；进度仍留在状态栏。 |
| P2 | 离线真实 UI 脚本在曝光滑杆步骤失败；默认“范围”模式下找到了隐藏滑杆，却没有真正点选图层。界面列表之前仍把当前层显示成选中绿色。 | “当前数据层”与“用户点选用于调整的层”是不同状态，但脚本和行颜色混用。 | 脚本先点击真实图层行并断言滑杆可见；行高亮改由 `pickedLayerId` 决定，列表增加操作提示。 |
| P2 | 24MP 图上 3 个元素预计算结束后，有 1 个无法可靠分割，但该行仍提示“预计算中”，用户会继续等待；全局提示此前还只报单个任务结果。 | 元素清单只有 `pixelReady` 布尔值，无法区别等待、失败和尚未启动；状态文字未汇总清单。 | `SceneIndex` 增加逐元素状态：`pending / ready / unavailable / idle`；行提示提供重试或手动选择，全局状态显示已就绪/总数和失败数。 |
| P3 | 选区生成后，滚动区和固定输出条各有一个“新建调整层”主按钮，增加重复决策。 | 同一落地动作被两个 QML 区域分别实现。 | 删除滚动区的重复按钮，只保留始终可见的 `DraftOutputBar`。 |
| P3 | README 仍教用户寻找已删除的“元素/选区/调整”标签，且声称 RAW、修复画笔不可用，版本与项目格式也落后。 | 产品导航迭代后入口文档没有同步。 | 更新入门操作、支持格式、局限与当前版本；链接到本轮问题记录。 |

## 架构结论

单 worker 保证图像状态一致，但“低优先级”必须有小任务粒度，才能让点击、预览和导出真正插队。元素轮廓缓存的有效期由 **源图摘要 + 清单版本** 决定，不应由滑杆和草稿的编辑代数决定。界面选择状态也应以用户明确点选的图层为准，避免数据层与视觉选中态冲突。

## 第三轮：首次元素轮廓等待

| 优先级 | 亲测问题 | 根因与修改 |
|---|---|---|
| P1 | 云端画面分析返回后，用户还要等本地首个元素编码，首次悬停或点选的响应慢。 | 场景请求发出时没有启动本地编码，元素清单返回后才在低优先级任务中首次加载模型和编码。现在分析请求发出前排入低优先级预热，与云端等待并行；清单结果沿用同一张图的编码缓存。重复预热请求不再排队，预热结果也不覆盖正在显示的 AI 进度。 |
| P2 | 本机冷编码约 3 秒以上，单个任务仍无法中断。 | EfficientSAM 的 CPU 执行原来固定为 4 线程。实测 8 线程较快；现在按可用逻辑核心数选取，最多 8 线程，保留模型输入尺寸与权重。 |
| P2 | 换照片时旧预热返回“选区已取消或过期”，让用户以为刚才的操作失败。 | 旧预热与用户发起的点选共用过期提示。现在后台预热过期时静默丢弃；预热错误只有在当前照片仍有效且没有前台/待处理任务时提示。 |
| P2 | 元素清单返回后状态栏仍说“正在生成像素选区”，看不出轮廓是后台准备，也不知道可继续操作。 | AI 返回的统一收尾文案只检查是否有 `segment` 请求，没有区分场景清单与用户发起的选区。现在场景结果明确显示元素轮廓后台准备及可继续操作。 |

`scripts/benchmark_sam_encode.py` 在同一张 1600px 示例图上的独立进程测量：4 线程编码约 3.35 秒，8 线程约 2.91 秒；把输入边长从 1600 降到 1024 并没有明显减少编码耗时，因此没有牺牲轮廓输入分辨率。基准会受并行进程影响，数字用于比较本机配置，不作为所有机器的保证。

`scripts/qa_scene_preheat.py` 使用真实 Qt 编辑器、worker 和 EfficientSAM，以本地模拟接口固定延迟云端响应约 6 秒，使用两张像素不同的 12MP 合成照片，并为每次运行创建独立临时编码缓存。可复测的冷缓存对照：未预热时元素清单约 6.23 秒返回，之后轮廓任务约 5.47 秒结束；并行预热时本地编码约 3.98 秒完成，清单约 6.22 秒返回，之后约 0.89 秒结束。两次各有 2/3 个元素获得可靠轮廓，质量限制未因调度改变。若云端请求快于本地编码，用户仍会等正在执行的单个任务；这部分等待尚未消除。

本轮场景预热及状态文案修改前的完整回归为 `286 passed, 1 skipped`（106.60 秒）；状态文案另做定向复测。

## 第五轮：预热与画布操作解耦

| 优先级 | 亲测问题 | 架构根因与修改 |
|---|---|---|
| P1 | 取消冷缓存点选后立刻画矩形，预览仍要约 3.89 秒；立刻换照片约 4.06 秒。 | 可选的照片编码仍在负责导入、渲染、导出的主 worker 中执行，队列优先级无法中断已开始的 ONNX 推理。现在按需启动独立短进程编码主 worker 已生成的 1600px 代理图；主 worker 可同时处理画布和文件操作。 |
| P1 | 冷预热时点选若直接进主 worker，会与独立进程重复编码并争用 CPU。 | 主调度器以前只判断主 worker 是否空闲。现在预热期间保留像素请求在队列中，其他渲染/导入任务照常执行；预热完成后从磁盘读取相同图片的嵌入，再做轮廓解码。 |
| P2 | 用户取消等待中的点选或换照片，后台编码继续占 CPU。 | 旧预热与主 worker 绑定，无法单独终止。现在取消等待点选或换图会结束独立预热进程；关闭窗口也等待它退出。 |

真实 QML 冷缓存对照（`scripts/qa_cold_pixel_queue.py`，4K×3K 合成图）：改造前取消后画框预览约 3.89 秒、换照片约 4.06 秒；改造后在预热进程已运行 0.8 秒时点击取消，编码进程约 0.00–0.02 秒退出，画框预览约 0.06 秒、换照片约 0.16 秒。不取消而直接切矩形工具，预热同时运行时画框预览约 0.09 秒；不先点选而直接换照片约 0.17 秒。取消预热后再次点像素目标需重新冷编码，本机约 4.47 秒，符合取消释放资源的含义。

真实 worker + 本地模拟 AI 的冷缓存对照（`scripts/qa_scene_preheat.py`）：未预热时清单返回后轮廓约 5.80 秒完成；独立预热约 3.98 秒完成并与约 6.25 秒的云端等待重叠，清单返回后约 1.78 秒完成。预热组首次轮廓报告 `embedding_disk=true`，基线为 `false`；两组仍各有 2/3 个可靠轮廓。场景分析等待时间无明显变化。

本轮完整测试集 `289 passed, 1 skipped`（102.21 秒）；真实界面脚本覆盖取消、预热期间画框、直接换图及缓存复用。之前第四轮记录中的“取消后仍等当前编码释放”描述的是主 worker 预热旧架构，本轮已消除该阻塞；已开始的交互分割本身仍不可中断。

## 第六轮：执行中的取消与后台轮廓隔离

| 优先级 | 亲测问题 | 架构根因与修改 |
|---|---|---|
| P1 | 真实 QML 中，点选已进入分割计算后点击取消，界面仍需约 3.58–3.75 秒解除忙碌；此前只能丢弃结果，不能立即画框或换图。 | 前台分割仍在主 worker 执行，取消只能标记请求。新增按需启动的持久 `pixel_worker.py`；所有交互分割改走独立队列。取消执行中的请求直接结束像素进程，主 worker 保持可用。 |
| P1 | 后台计算元素轮廓时，2400 万像素照片上画框预览约 4.17 秒才出现。 | 低优先级轮廓仍占用主 worker，队列只能在单个对象完成后调度。后台轮廓也移到像素进程；前台点选到来时中断当前后台对象并在重启后优先处理，旧对象排到后面。 |
| P1 | 后台轮廓正在计算时换照片，旧对象可能继续占用 CPU 或让新照片导入排队。 | 旧任务没有与照片生命周期绑定。换图时清除旧照片的低优先级请求并结束活跃的后台像素进程；旧结果仍按照片摘要与元素清单版本隔离。 |
| P2 | 前台点选结束后，后台元素进度可能马上覆盖“选区已生成”的状态文案。 | 后台结果直接改写全局状态。已有选区草稿或 AI 任务时保留用户当前状态，元素行仍更新实际轮廓状态。 |
