# iPhoto 1.4 交付与验收

验收日期：2026-09-23。按 [本轮计划](plan.md) 完成，源码入口与扩展方法见 [仓库说明](../../docs/repository-guide.md)。

## 体验变化

- **文字选区**：先分析主要画面元素，再选择/排除对象 id，复用已有轮廓。清单没包含目标时保留“直接识别此目标”。修复千问原样返回格式定义、扁平坐标列表导致失败的两类实际问题；不猜测缺失坐标或放宽非法数值。
- **画面元素**：类别勾选、单项勾选、新选区、添加、减去、相交。清单随项目保存；重新打开不自动调用 AI。首次分析可取消，最长等待 90 秒。
- **点选**：O 为对象点选，先悬停看轮廓，再点击；重叠处优先较小对象，大背景可以在清单明确勾选。W 明确为连续颜色魔棒。Shift 添加、Alt 减去，所有结果先进入草稿。
- **边缘**：默认不自动覆盖 AI 轮廓。手动优化已有对象轮廓时保留内部，只重新判断较窄的边缘带；粗框使用原有前景发现方式。失败保留草稿，成功可撤销。
- **图层组**：此前只有平铺层，本版实现真正的四级组嵌套。支持组内新建、移入/移出、同级排序、折叠、整组复制/删除、可见性、组蒙版和不透明度、撤销/恢复。合计最多 32 项。
- **小窗口**：选区期间默认收起图层详情，保证对象清单、组合和输出按钮可见；仍可点“图层 +”展开。选中组时显示组操作说明和新建调整层入口。

## 代码与性能

界面分为 9 个区域组件和共享控件。Editor 保留唯一 QObject 门面，业务委托到 6 个 controller 模块；AI 网络与请求协议分开；对象索引与层级规则为独立领域模块。Python 代码统一格式，静态检查通过。

图层合成缓存现在支持嵌套子树，改变组不透明度可以复用组内结果。未变化的蒙版预览不再反复编码 PNG。悬停命中使用预计算索引，既不重新分割也不调用云端。

同一台机器、同一进程对内置湖景的 1600×1066 RGB 预览独立测量；一层全图调整加一个含两层调整的组，每种变化采样三次。以下仅为 CPU 合成，不含 PNG、进程通信和 Qt 显示，不代表原尺寸导出耗时。

| 场景 | 缓存中位耗时 | 完整重算中位耗时 | 减少 |
|---|---:|---:|---:|
| 改组不透明度 | 23.69 ms | 1469.42 ms | 98.4% |
| 改组内最上层参数 | 705.51 ms | 1684.20 ms | 58.1% |

两条路径逐像素相同。缓存逻辑像素占用 66,518,400 bytes，在 64 MiB 预算内；该预算不等于整个进程的内存上限。10 个真实 AI 元素建立点选索引耗时 13.924 ms，10,000 次命中查询共 168.845 ms，均值约 16.9 微秒。原始数据：[性能报告](../../artifacts/v14-benchmark.json)；重现：`scripts/benchmark_v14.py`。

## 自动化验收

最终完整运行：**137 passed、1 skipped，133.84 秒**。跳过的是测试沙箱无法读取登录凭据会话的 Windows 凭据用例，随后在正常 Windows 会话单独补跑 **1 passed，1.41 秒**。合计 **138 个不同测试用例通过**，没有将重复运行累加为新用例。

静态检查：`ruff check src --select F` 通过；`ruff format --check src` 通过。

本轮新增 32 个测试实例，覆盖：

- 真实故障对应的 JSON Schema 回显、扁平/奇数坐标、非有限值、截断；非法/重复/冲突的对象 id。
- 一次画面分析后接对象选择的完整双请求流程；复用清单不上传照片；取消首次分析不触发后续请求。
- 同类组合、并集/差集/交集、选区外逐像素不变；命中优先级与鼠标移动不重新光栅化。
- 嵌套组透明度数学、隐藏继承、循环/非法/过深父链、子树复制 id、缓存与完整重算一致。
- 图层组移动、删除与撤销、恢复场景清单和草稿；保留已有多色对象内部的修边。
- 1440×930、1080×700 下真实 Qt 鼠标、悬停、Shift/Alt 点选、组合、输出、编组、移出和输入焦点隔离。

原有照片加载、色彩、导出、透明通道、参数锁定、建议保存、恢复失败保护和连接配置测试继续保留。UI 模拟数据截图有明确 `mock` 命名：[小窗口元素面板](../../artifacts/v14-objects-mock-1080.png)、[嵌套组](../../artifacts/v14-groups-mock-1440.png)。

## 真实千问验收

在用户明确授权后，使用本机 Windows 凭据库中已保存的 Token Plan 配置和 **qwen3.8-flash**，只测试内置 `assets/lake.jpg`。共 10 次真实请求，不在脚本参数、源码、文档或记录中写 Key。

| 阶段 | 实际观察 |
|---|---|
| 原协议，2 次 | HTTP 200；一次返回 JSON Schema 而不是选区，一次返回扁平坐标，均被原解析器拒绝。 |
| 修正直接轮廓协议，2 次 | 两次均生成草稿；木屋较合理，但天空误选到左上角树枝附近。因此没有把解析成功当成体验问题已经解决。 |
| 元素协议，1 次 | 29.52 秒，返回 9 个主要元素；天空轮廓比直接描边合理，但边缘仍粗。 |
| 实际编辑器完整流程，3 次 | 首次分析在旧 60 秒截止时超时，保留原状态。另一轮分析和对象选择共 29.16 秒，返回 10 个元素并组合木屋与栈道。随后将场景截止时间调为 90 秒，未自动重试。 |
| 保存清单后的文字选择，2 次 | 天空并排除树木/山峰：2.33 秒；木屋与栈道：2.20 秒。两次生成草稿，都只发送对象清单与要求，不再次上传照片。 |

真实记录：[原始失败](../../artifacts/v14-live-baseline/report.json)、[直接描边](../../artifacts/v14-live-protocol-fixed/report.json)、[完整流程](../../artifacts/v14-live-workflow/report.json)、[清单复用](../../artifacts/v14-live-warm/report.json)。

效果证据：[天空排除前景后的覆盖图](../../artifacts/v14-live-warm/0-selection.png)、[木屋与栈道覆盖图](../../artifacts/v14-live-warm/1-selection.png)。天空靠树枝和山脊处仍有粗边、漏选；这是一张照片的验收，不能据此声称在人像、室内和所有风景上达到稳定分割精度。

相关依据：[千问视觉定位文档](https://help.aliyun.com/en/model-studio/vision)介绍了归一化坐标的定位方式；应用明确要求整图 0～999 坐标并校验，仍需要检查模型是否选对目标。[OpenCV GrabCut 官方教程](https://docs.opencv.org/4.x/d8/d83/tutorial_py_grabcut.html)区分确定与可能前景/背景，本版据此对已有轮廓保留内部确定前景。

## 可直接试用的示例

[v1.4 示例项目](../../artifacts/v14-demo.iphoto)包含 10 个真实 AI 画面元素、天空/木屋选区和两级嵌套组。示例调色参数为本地设置，用于展示蒙版与图层组，不是额外 AI 调色调用；对话中也有说明。

```powershell
.venv\Scripts\python.exe run.py --project artifacts/v14-demo.iphoto --scene-panel
```

元素、选区和组都可继续编辑；项目引用内置湖景源文件。尚不支持 PSD 像素层、所有 Photoshop 混合模式、发丝级抠图、生成式局部重绘和曲线等高级工具。本轮完善的是已实现工作流、代码边界与可验证性能。
